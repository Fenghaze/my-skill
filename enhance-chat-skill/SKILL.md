# 增强对话规划技能

## 概述

本技能通过严谨的设计树方法论增强规划模式下的规划过程。它系统性地探索需求、提出详细问题、并确保完整的功能规范，从而最小化从设计到实现过程中的 bug。

## 使用时机

**强制触发规则：凡涉及功能相关的请求，一律先调用此技能。**

**触发前自检清单（在调用本技能前自我检查）：**
- [ ] 这个请求是否涉及修改代码？（如果是 → 必须触发）
- [ ] 这个请求是否涉及优化/改进现有功能？（如果是 → 必须触发）
- [ ] 这个请求是否涉及修复bug？（如果是 → 必须触发）
- [ ] 这个请求是否涉及添加新功能？（如果是 → 必须触发）
- [ ] 这只是一个简单的读文件/看代码/查文档操作？（如果是 → 无需触发）

**强制触发场景：**
1. 用户请求新增功能（如"添加XX功能"、"实现XX"）
2. 用户请求修改或优化现有功能（如"改进XX"、"重构XX"、"优化XX"）
3. 用户请求删除功能（如"移除XX功能"）
4. 用户请求修复功能bug（如"XX功能有问题"、"修复XX"）
5. 用户进入规划模式进行软件设计任务
6. 用户使用 /plan 命令或类似规划命令
7. 用户询问架构设计或系统规划
8. **任何需要写代码才能完成的任务请求**（除非是简单的读文件、看代码、查文档）
9. 用户询问功能建议（如"还能加什么功能"、"有什么好功能可以加"）
10. 用户询问项目扩展方向

**禁止行为：**
- 禁止在未经此技能进行需求分析和颗粒度对齐的情况下直接开始写代码
- 禁止对模糊需求直接实现，必须先通过此技能澄清
- **⚠️ 关键检查点：任何涉及"修改代码"、"优化"、"改进"、"修复"、"添加功能"的请求，必须首先调用 `Skill` 工具激活本技能**

## 设计树方法论

设计树将需求从高层目标分解为具体的、可测试的规范：

```
目标（用户目标）
  └─ 领域分析
       └─ 用例场景
            └─ 功能点
                 └─ 需求细节
                      └─ 边界情况
                           └─ 异常处理
```

## 规划工作流程

### 阶段0：颗粒度对齐

**目的：** 明确项目类型，确定后续规划的广度和深度

**必须询问用户：**

> "请确认本次开发的颗粒度：
> 1. **0-1项目搭建** - 从零开始的新项目，需要完整技术选型、架构设计
> 2. **已存在项目的业务功能实现** - 在现有项目上添加功能，最小化改动
> 3. **功能bug修复** - 修复现有功能的错误，快速定位
> 4. **功能建议/扩展咨询** - 了解项目可扩展方向（自动分析 + 给出建议）"

**不同颗粒度的规划策略：**

| 颗粒度 | 规划深度 | 设计树展开 | token消耗 | 目标 |
|-------|---------|-----------|----------|------|
| 0-1项目搭建 | 完整展开 | 全链路 | 高 | 技术选型+架构设计 |
| 业务功能实现 | 中等 | 聚焦新增部分 | 中 | 最小化改动 |
| Bug修复 | 轻量 | 问题定位 | 低 | 快速修复 |
| 功能建议/扩展咨询 | 轻量 | 分析后生成建议 | 低 | 明确方向再深入 |

**0-1项目搭建：** 完整使用设计树方法论，从技术选型→架构设计→详细设计

**业务功能实现：**
- 聚焦于「新增/修改」部分
- 优先复用现有架构和模式
- 使用 `Agent` 工具 + `Explore` 子代理推断技术栈和架构（减少交互）
- 设计树只展开新增功能的路径

**Bug修复：**
- 不使用完整设计树
- 使用 `Agent` 工具 + `Explore` 子代理定位问题根因
- 问：「出错的输入是什么？预期行为是什么？」
- 给出最小改动修复方案

**功能建议/扩展咨询：**
- 自动分析现有项目（读取代码）
- 基于分析结果生成 3-5 个功能扩展建议
- 用户选择感兴趣的方向后，再进入对应颗粒度的需求分析

### 阶段0.5：功能建议模式（新增）

**触发条件：** 用户询问"还能新增哪些功能"、"有什么好功能建议"等开放式问题

**工作流程：**

1. **自动分析项目**（使用 Agent 子代理，无需用户交互）
   - 使用 `Agent` 工具 + `Explore` 子代理类型深入探索代码库
   - 分析现有功能列表、路由处理、数据结构
   - 分析技术栈和架构模式
   - 分析 UI/UX 当前实现程度
   - **注意**：必须用子代理探索，不能直接用 Glob/Grep/Read 盲目搜索

2. **生成功能建议列表**
   - 基于分析结果，推荐 3-5 个高价值可扩展方向
   - 每个建议说明：解决什么问题、对现有架构的影响、实现复杂度

3. **用户选择感兴趣的方向**
   - "你对哪个方向感兴趣？"
   - 用户选择后，进入对应颗粒度的需求分析

**功能建议模式的简化设计树：**

```
项目现状分析
├─ 现有功能清单
├─ 技术架构评估
├─ 数据模型评估
└─ UI/UX 成熟度评估
     ↓
功能扩展建议
├─ 建议1：[功能名] - [解决什么问题] - [复杂度]
├─ 建议2：[功能名] - [解决什么问题] - [复杂度]
└─ 建议3：[功能名] - [解决什么问题] - [复杂度]
     ↓
用户选择方向
     ↓
进入标准需求分析流程（阶段1）
```

**与标准流程的区别：**

| 对比项 | 标准流程 | 功能建议模式 |
|-------|---------|-------------|
| 触发 | 明确需求 | 开放式咨询 |
| 初始分析 | 用户回答问题 | 自动分析项目 |
| 设计树 | 从用户回答展开 | 从分析结果生成建议 |
| 交互轮次 | 多轮提问 | 1轮选择 + 后续提问 |
| 目标 | 收集完整需求 | 明确方向后再收集需求 |

### 阶段1：深度需求收集

**根据颗粒度调整问题深度：**

**0-1项目搭建 - 完整提问：**
1. **业务背景**
   - 我们要解决什么问题？
   - 用户是谁？
   - 成功指标是什么？

2. **功能需求**
   - 核心功能有哪些？
   - 有哪些边界情况？
   - 错误时应该如何处理？

3. **非功能需求**
   - 性能要求（延迟、吞吐量）
   - 可扩展性考虑
   - 安全要求
   - 可用性要求

4. **集成点**
   - 外部 API/依赖
   - 数据源
   - 需要集成的现有系统

5. **约束条件**
   - 技术约束（语言、框架）
   - 时间/预算约束
   - 团队专业能力

**业务功能实现 - 轻量提问：**
- 新增功能的核心需求是什么？
- 对现有架构的影响范围？
- 需要复用哪些现有组件/模式？

**Bug修复 - 快速提问：**
- 出错的输入是什么？
- 预期行为是什么？
- 实际行为是什么？
- 最近一次正常是什么时候？

### 阶段2：设计树展开

**根据颗粒度调整展开深度：**

**0-1项目搭建 - 完整展开：**

对每个功能进行系统性展开：

```
功能：[功能名称]
├─ 主路径：[正常流程描述]
├─ 替代路径：[替代流程]
├─ 错误场景：
│   ├─ [错误类型1] → [恢复操作]
│   ├─ [错误类型2] → [恢复操作]
│   └─ ...
├─ 边界情况：
│   ├─ [边界情况1] → [预期行为]
│   ├─ [边界情况2] → [预期行为]
│   └─ ...
├─ 输入验证：
│   ├─ [字段1]：[约束、有效范围]
│   ├─ [字段2]：[约束、有效范围]
│   └─ ...
└─ 输出规范：
    ├─ [成功输出格式]
    ├─ [错误输出格式]
    └─ ...
```

**业务功能实现 - 聚焦新增：**
- 只展开新增/修改的功能路径
- 复用部分用「沿用现有架构」标注

**Bug修复 - 跳过设计树：**
直接进入问题定位

### 阶段2.5：并行执行指引（新增）

**当识别出多个独立任务时，自动拆分并行执行以提升效率。**

**可并行的场景：**
- 多个独立功能同时开发（如"用户模块"和"订单模块"无依赖）
- 功能实现 + 测试用例构建可并行
- 前端实现 + 后端实现可并行
- 数据模型设计 + API 设计可并行

**并行执行规则：**
1. 使用 `Agent` 工具启动多个子代理并行执行
2. 每个子代理专注单一任务
3. 主代理负责协调结果和最终整合

**示例：**
```
用户请求："添加用户模块和订单模块"

主代理拆分：
├── Agent A: 实现用户模块（routes/users.js, data/users.js）
├── Agent B: 实现订单模块（routes/orders.js, data/orders.js）
└── Agent C: 编写测试用例（并行或后续执行）

主代理整合：
├── 合并路由到 app.js
├── 验证功能完整性
└── 生成最终测试报告
```

**不适用的场景：**
- 任务有先后依赖（如先设计数据库才能写 API）
- 任务是单一职责的简单修改
- 涉及跨多文件的协调改动（如架构重构）

### 阶段3：风险评估

**根据颗粒度调整：**

| 颗粒度 | 风险评估深度 |
|-------|------------|
| 0-1项目搭建 | 完整风险矩阵 |
| 业务功能实现 | 聚焦改动带来的风险 |
| Bug修复 | 最小化改动，避免引入新问题 |

### 阶段4：TDD 验证策略（强化）

**核心原则：测试先行，确保每个功能的可靠性。**

**TDD 工作流：红-绿-重构**

```
1. 红（Red）  → 先写失败的测试用例，明确预期行为
2. 绿（Green）→ 写最简代码让测试通过
3. 重构（Refactor）→ 优化代码，保持测试通过
```

**验证策略（根据颗粒度）：**

| 颗粒度 | 验证策略 |
|-------|---------|
| 0-1项目搭建 | 完整测试策略 + 验收标准 + TDD |
| 业务功能实现 | **必须先写测试**，再实现功能 |
| Bug修复 | 先写复现测试 → 修复 → 验证 |

**业务功能实现的 TDD 强制要求：**

> ⚠️ **禁止跳过测试直接实现功能**

```
正确流程：
1. 明确功能需求和验收标准
2. 先写测试用例（明确预期）
3. 运行测试确认失败
4. 实现功能
5. 运行测试确认通过
6. 重构（如需要）
7. 最终验证
```

### 阶段4.5：完整测试流程（强制）

**核心原则：功能再小，也要执行完整测试流程，保证产品质量。**

**完整测试流程（任何代码改动后必须执行）：**

```
1. npm test        → 运行 Jest API 测试
2. npx playwright test → 运行 E2E 测试
3. 分析测试结果   → 区分"我的改动导致" vs "既有测试问题"
4. 如有问题       → 定位根因并修复
5. 全部通过       → 才能算完成
```

**测试结果分析判断：**

| 失败类型 | 判断方法 | 处理方式 |
|---------|---------|---------|
| 我的改动导致 | 失败用例与改动逻辑相关 | 修复我的代码 |
| 既有测试问题 | 失败与改动无关（如测试隔离、数据污染） | **也要修复**，保证产品质量 |

**⚠️ 产品质量意识：**
- 即使测试失败"不是我的问题"，也要主动修复
- 测试稳定性问题（如数据污染、测试隔离）会累积，最终影响交付质量
- 发现一个修复一个，保持测试套件始终可靠

**验证检查清单：**

- [ ] 核心功能测试通过
- [ ] 边界情况测试通过
- [ ] 错误处理测试通过
- [ ] `npm test` 全套通过
- [ ] `npx playwright test` 全套通过（无稳定性失败）
- [ ] 功能确实可用（手动验证）
- [ ] 如有测试稳定性问题，已记录并计划修复

**测试用例优先级：**

| 优先级 | 测试类型 | 说明 |
|-------|---------|------|
| P0 | 核心功能测试 | 主路径必须通过 |
| P1 | 边界情况测试 | 0、空值、极端值 |
| P2 | 错误处理测试 | 异常输入、权限验证 |
| P3 | 集成测试 | 多组件协同 |

## 必问问题类别

- "此功能的精确用户旅程是什么？"
- "当 X 失败时会发生什么？"
- "系统应该如何处理 [边界情况]？"
- "性能期望是什么？"
- "谁需要批准此设计？"

### 数据问题
- "需要存储什么数据？"
- "如何处理数据验证？"
- "数据关系是什么？"
- "如何处理并发访问？"

## 交付成果

使用此技能时，输出应包括：

1. **需求摘要**：完整理解需要构建什么
2. **设计树可视化**：系统的分层分解
3. **详细规格**：对每个功能包括：
   - 描述
   - 输入/输出规范
   - 错误处理
   - 边界情况
   - 测试场景
4. **风险矩阵**：已识别的风险及缓解策略
5. **实施计划**：带依赖关系的分步执行计划

**颗粒度对交付的影响：**
- 0-1项目搭建：完整交付以上5项
- 业务功能实现：聚焦1-3项，实施计划侧重新增部分
- Bug修复：问题描述 + 根因 + 修复方案 + 验证方法

## 应避免的反模式

- ❌ 未确认就做假设
- ❌ 因为"罕见"而跳过边界情况
- ❌ 延迟错误处理决策
- ❌ 编写模糊的规范
- ❌ 忽略性能影响
- ❌ 忘记安全影响
- ❌ 不考虑向后兼容性
- ❌ 规划时没有测试策略
- ❌ 对所有项目使用相同的规划深度（应按颗粒度调整）
- ❌ **跳过测试直接实现功能**（TDD 违规）
- ❌ **改动代码后不运行测试**（完整测试流程违规）
- ❌ **测试失败不分析原因直接忽略**（产品质量意识缺失）

## 应用示例

### 0-1项目搭建示例

当用户说"新建一个电商后台系统"时，技能应展开为完整设计树。

### 业务功能实现示例

当用户说"在现有电商系统中添加拼团功能"时：
- 先读取现有代码推断架构
- 设计树只展开拼团功能相关路径
- 复用现有用户/订单/支付模块
- **必须先写测试用例，再实现功能**

### Bug修复示例

当用户说"用户无法登录，报500错误"时：
- 不使用完整设计树
- 直接定位问题根因
- 先写复现测试 → 修复 → 验证
